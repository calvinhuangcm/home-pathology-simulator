## 2026-10-16：旋轉視角的壁癌顯示修正

使用者要求保留全部情境功能，只移除卡片及場景副標題的「舊版示意」文字。七張卡片均可選取；02A 加入 🚿、02B 加入 🚰，使用既有的圖示容器與卡片排版。未移植情境的副標題仍說明「尚未接上網格引擎」。

重現問題：窗框、管線案例的半透明白華／黴菌物件會先寫入深度；正常牆面本身也使用透明材質，旋轉時可能被這些深度擋住，露出後方磚層，形成塊狀破圖。

修正方式：

- 外觀模式的牆殼使用不透明材質，先建立正確遮擋；剖面模式才啟用透明，並按外層到內側飾面的順序混色。
- 半透明白華與黴菌不寫入深度，固定與濕痕的繪製順序，同時保留深度測試。
- 網格症狀貼圖對齊實際牆面／天花，使用 polygon offset 避免重疊閃爍；依觀察面使用單側繪製，並提高斜角貼圖的各向異性過濾品質。

新增 `tests/rendering-browser.mjs`，可用 `./scripts/run.sh test:browser:rendering` 執行，也包含在完整 `test:browser` 中。測試涵蓋全部情境仍可選取、指定文字已移除、兩個圖示存在，以及窗框／管線的正面、左右斜角與俯視畫面；在受損區域實際截圖取樣，每個角度皆未偵測到穿透完整粉光面的紅褐色磚塊像素。另實際旋轉已受潮的 Scenario 01 牆面及 Scenario 02A 天花，並檢查剖面切換、暫停與 console／runtime errors。

### 最終挑戰指出的未覆蓋風險

Gemini 提醒 20× 播放遇到主執行緒卡頓時的長幀風險。程式檢視確認其「單幀可能補算數百 tick」的說法不符合目前呼叫路徑：動畫每次傳入引擎前以 `Math.min(.1, elapsedSeconds)` 封頂；20× 且固定步長 0.05 秒時，每次最多 40 ticks，背景分頁則直接暫停。引擎仍可能在慢速裝置或較長卡頓後執行這批補算而出現延遲，因此真實瀏覽器／Android 的 20× 長任務與渲染影格分位數尚未量測；需要在目標裝置記錄 UI thread long tasks、每幀 tick 數與 simulation-time throughput 後，再決定是否加 tick 上限。直接丟棄累積時間會降低教學時鐘速度，不應未量測就加入。

另以 Playwright 在本機 Chrome headless 對 20× 做一次 5 秒暖機後的 5 秒觀察：模擬時間前進 100.35 秒，錄到 301 個 RAF，間隔 P50 16.7 ms、P95 16.8 ms；觀察到 1 個 66 ms Long Task，page errors 為 0。這支持本機測試環境可維持約 20× 模擬吞吐；單次 headless 觀察無法定位該 Long Task 的來源，也不足以證明穩定 60 FPS、低階裝置或 Android 表現。此結果保留為待實機 profile 的風險，不據此加會丟棄模擬時間的硬性 tick 上限。
